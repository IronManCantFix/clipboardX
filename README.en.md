# ClipboardX

![Build](https://github.com/IronManCantFix/clipboardX/actions/workflows/build.yml/badge.svg)

A modern, minimal clipboard manager for macOS — native feel, fully offline, low memory.

[简体中文](README.md)

## Features

- **Global shortcut** — summon the popover anywhere with `⌘⇧V` (customizable)
- **Clipboard history** — text, URLs, files, folders, images (PNG/JPEG/GIF/TIFF/HEIC)
- **Smart dedupe** — copying the same content again moves it to the top instead of duplicating
- **Instant search** — fuzzy or exact matching, case-insensitive, under 50ms
- **Pin** — keep important entries pinned on top (pinned items are never auto-cleaned)
- **Images** — thumbnail previews in the list; originals saved at full resolution (pasting restores the complete image), loaded on demand
- **Global dedupe** — duplicate content moves to front without repetition
- **Screen-aware positioning** — the popover stays near your cursor, avoids screen edges, and follows the cursor across multiple displays
- **Auto cleanup** — by count (default 15, up to 100) with pinned items protected
- **Menu-bar app** — no Dock icon, launches at login (optional)
- **Fully offline** — no network, no telemetry, no cloud

## CI Build

GitHub Actions builds the macOS (Apple Silicon) app on every tag push (`v*`) and **auto-publishes** it to GitHub Releases (no manual steps): build artifacts (`.dmg` / `.app.zip` / update package `.app.tar.gz` + `.sig` / update manifest `latest.json`) and the changelog are uploaded and published together — see [`.github/workflows/build.yml`](.github/workflows/build.yml). Once published, the in-app “Check for Updates” can fetch the new version via `releases/latest/download/latest.json` and auto-install it.

The changelog is generated by [`scripts/generate-release-notes.py`](scripts/generate-release-notes.py): grouped by `fix:` / `feat:` / `perf:` etc., with release date, change range, commit count and short hashes, plus a full commit-compare link. To override, place a `RELEASE_NOTES.md` at the repo root — its content fully replaces the auto-generated changelog.

### Releasing a new version (tag-only)

The version comes from the tag — CI injects it into both `Cargo.toml` and `tauri.conf.json` automatically, so **no manual version edits**:

```bash
git tag v0.1.19
git push origin v0.1.19
```

CI then does everything: inject version → build → minisign sign → generate changelog → publish the release. Users get the update via the in-app “Check for Updates”.

> Tags must be `vX.Y.Z` (e.g. `v0.1.19`; pre-releases like `v0.1.19-beta.1` are allowed). To build a specific version locally, run `python3 scripts/bump-version.py v0.1.19` first, then `npm run tauri build`.

### Auto-update signing keys (one-time setup)

Update packages are signed with minisign. Generate the keys once locally (the private key lives in `updater-keys/tauri.key`, git-ignored — **never commit it**):

```bash
# Generate keys (-p is the password)
npx tauri signer generate -w updater-keys/tauri.key -p <password> --ci

# Write the base64 content of tauri.key.pub into plugins.updater.pubkey in src-tauri/tauri.conf.json
```

Then add two secrets in GitHub **Settings → Secrets and variables → Actions**:

- `TAURI_SIGNING_PRIVATE_KEY`: the **file content** of `updater-keys/tauri.key` (it is already base64 — copy it as-is, do not encode it again; see `updater-keys/README.txt`)
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the key password

> Losing the private key or password means you can no longer publish auto-updatable releases; you would need to regenerate keys and update `pubkey` in `tauri.conf.json` (older installs would then fail signature verification and need one manual install).

## Installing on macOS (unsigned app)

Builds from this repo are **not signed with an Apple Developer ID** (that requires a paid Apple Developer account) and are not notarized, so Gatekeeper blocks the first launch. Use any of these:

- **Option 1 (recommended): right-click → Open** — Control-click (or right-click) `ClipboardX.app` in Finder, choose **Open**, then click **Open** in the dialog.
- **Option 2: System Settings** — after the first blocked attempt, go to **System Settings → Privacy & Security**, find the ClipboardX warning and click **Open Anyway**.
- **Option 3: remove the quarantine flag** — run this once, then double-click normally:

  ```bash
  xattr -dr com.apple.quarantine /Applications/ClipboardX.app
  ```

If macOS says the app “is damaged and can't be opened” (usually a broken download or stripped signature), re-download it or run:

```bash
xattr -cr /Applications/ClipboardX.app
```

> Only install apps from sources you trust. There is no need to disable Gatekeeper entirely (`spctl --master-disable`).

## Accessibility Permission (required for auto-paste)

ClipboardX simulates `⌘V` to auto-paste, which requires macOS Accessibility permission. The system will prompt you on first paste.

Steps:

1. On first paste, the system shows an Accessibility permission dialog
2. Go to **System Settings → Privacy & Security → Accessibility**
3. Find ClipboardX and toggle it on
4. **Fully quit ClipboardX** (tray icon → Quit) and reopen it
5. Paste again — it should now work

> **Switching from dev to release builds**: if an old entry with the same name already exists in the Accessibility list, remove it first (click the minus button), then re-add the new version. macOS permissions are bound per-binary; different builds are not interchangeable.

## Data

All data stays local:

```
~/Library/Application Support/com.clipboardx.app/
├── entries.db      # history database
├── clipboardx.log  # runtime log (for diagnosing unexpected exits)
└── images/         # captured images (PNG)
```

## Troubleshooting unexpected exits

The app writes a file log. If it exits on its own, follow these steps:

1. **Runtime log**: open
   `~/Library/Application Support/com.clipboardx.app/clipboardx.log`.
   It records startup, exit events (`ExitRequested` / `Exit`), window destruction,
   listener restarts, a heartbeat every 10 minutes, and **panic locations with
   backtraces**. A `PANIC at ...` line is the crash point.
2. **macOS crash reports**: if the log ends with a heartbeat but no panic, the
   process died natively (e.g. SIGSEGV, which bypasses the Rust panic hook). Check
   the newest `ClipboardX-*.ips` file under `~/Library/Logs/DiagnosticReports/` —
   the crash type shows the signal (e.g. `SIGSEGV` / `SIGABRT`).
3. **Compare timelines**: match the last heartbeat/event timestamp in the log
   against the crash time in the report to bracket when and how it died.

> Dev builds log to `~/Library/Application Support/com.clipboardx.app.dev/clipboardx.log`.
